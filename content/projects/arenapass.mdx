## Overview

ArenaPass is a ticketing platform for arenas and venues. Buyers find events and pay for tickets, arena admins run their own venues, and a platform admin oversees the whole marketplace.

**Status: in active development.** It has not launched, so this write-up describes the design and the decisions made so far, not outcomes.

## Problem

Ticketing for a venue has three kinds of user with very different powers: people buying tickets, staff running one specific arena, and the platform operator. The hard part is not drawing three dashboards. It is guaranteeing that each user can only see and change what their role allows, even when a page has a bug.

## Architecture

A single Next.js 14 App Router application serves all three dashboards. Supabase provides authentication and the Postgres database. Paystack handles payment.

Every request passes through middleware that reads the session and the user's role and routes them to the right dashboard. Data access then goes through Supabase, where Row Level Security policies apply the same rules a second time.

## Key decisions & trade-offs

- **Roles enforced twice, at middleware and in the database.** Middleware gives fast redirects and a clean experience. Row Level Security means a missing check in application code cannot leak data, because Postgres refuses the query. The cost is that each rule is written in two places and the policies need their own tests.
- **One app with role-scoped routes, not three apps.** The dashboards share components, types and the data model. The trade-off is that route boundaries have to be kept strict so one role's code never ships to another.
- **Supabase instead of hand-rolled auth.** Auth identities plug straight into RLS policies, which removes a whole class of glue code. The trade-off is coupling to Supabase and Postgres policy syntax.
- **Paystack for payments.** It supports the payment methods buyers in Nigeria actually use.
